# Still assistant prompt contract

Runtime version: `still-assistant-1.1`. The shared [assembler](../extension/lib/ai-prompts.js) is imported by the authenticated [AI router](../bridge/ai/router.mjs). The server constructs the system instruction; a caller-supplied `body.system` is ignored. Provider selection, credentials, permissions, file reads, mutation validation and cancellation are enforced by application code rather than prompt prose.

The assistant has distinct contracts for chat, summaries, rewrites, task extraction, continuation, translation, explanation and finding connections. Edits preserve the user's meaning and supported facts. Task extraction distinguishes commitments from suggestions and preserves dates/owners only when supplied. The assistant is asked for usable output and concise explanations, not private chain-of-thought.

Source context includes stable item IDs, titles, source URLs, revisions, personal notes, article text, descriptions, highlights/annotations and relationships. Explicit selections rank first. Library search is lexical, local and bounded; broad library requests can include admitted items. At most 24 sources and a bounded character budget are included. Total text packing also bounds history and the draft; the token-window setting uses a conservative character heuristic, not an exact provider tokenizer. Archived items enter automatic context only when explicitly selected. Truncation is recorded, and the prompt forbids claiming to have inspected omitted files, URLs or an entire library. Binary files are not silently sent; explicitly chosen supported raster images can be attached to image-capable API connections.

Current-space context admits active items in the selected collection and its descendants, or uncollected items for Inbox. Its description and counts are a citable metadata source. Explicitly selected extra items remain visible as context chips. Missing or deleted spaces fail instead of expanding to the library. Changing spaces starts a separate conversation and aborts an owned in-flight answer; the previous answer keeps its original space and status.

The current request, draft, selected text and source records are JSON-encoded in a user message. Saved material is untrusted reference data and cannot authorize commands, select a provider or override instructions. Claims based on saved material use `[[item-id]]`; the UI links only IDs actually admitted for the response, including valid space metadata citations. This verifies citation membership, not whether every claim is entailed. Missing or conflicting evidence must be described rather than invented.

Answers from this assembler are drafts: the writing chat built on it has no library mutation tools (the library assistant below proposes changes for review, or applies the kinds the user allows). **Save as note**, **Append**, **Insert**, and **Replace** are separate user choices. Applying to a note stages an unsaved edit; the ordinary Save action uses the note's revision and preserves a conflicting draft. Coding agents use the separate MCP surface, which validates mutation fields, versions, destructive confirmation and applied receipts.

## Library assistant (`still-assistant-3.1`)

The assistant panel and page use a separate prompt, `assistantSystemPrompt` in [ai-prompts.js](../extension/lib/ai-prompts.js), with the same evidence rules and library tools from [lib/ai/tools.js](../extension/lib/ai/tools.js). Read tools run at once: `search_library`, `list_items` (browse by collection, type, tag, favorite, pinned and state, including archived items and Trash), `get_items`, `lookup_urls` (every item with the same canonical address), `list_collections`, `list_tags`, `get_page` (only with an attached page), `get_dashboard` (only when the app passed a dashboard adapter to `init`), and `search_ai_threads` and `get_ai_threads` (see [AI threads](#ai-threads-threadkeeper)).

Write tools never write on their own. The write calls of one model step become one proposal. By default it is a card: the user can leave items out (`onProposal` resolves to `'apply'`, `'discard'` or `{ decision: 'apply', exclude: [ids] }`) and the engine removes those items before anything is written, so tool results and counts are exact. A proposal of kinds the user allows applies at once instead (see [Assistant permission levels](#assistant-permission-levels)). A turn can hold up to four proposals for review plus twelve applied automatically, so a later step can use ids an applied one created; after a discard the turn proposes nothing more. Writes cover collections (create, update, move, delete), real links (`save_links`: URLs kept as given, deduplicated within the request and against saved links, notes with the same address reported), moving, tagging (including library-wide `rename_tag` and `delete_tag`), favorites, archive and unarchive, Trash and restore, `convert_items` (for example notes into links), notes (with tags, an optional sticky color and an optional `parent_id` that makes the note a subpage of any live item; without a `collectionId` it joins that item's collection), item edits (title, description, url, note body, pinned, read, reminder), related-item links, `show_collection_on_dashboard` (a links widget, added last) and `import_ai_threads`.

Each applied proposal keeps a plain undo record (`patches`, `createdCollections`, `createdNotes`, `createdItems`, `collectionPatches`, `deletedCollections`, `widgets`, and `importedChats` when an import created chats) in the saved conversation; the facade's `undoProposal(record)` reverts it after a reload. Items the assistant created are deleted for good on undo only when untouched since; edited ones go to Trash. Created notes are removed newest first, so a subpage goes before the page it sits in, and an id already removed is skipped. Prior answers are replayed with a short list of the changes they proposed, their outcome and the ids involved, so a follow-up can correct an earlier change. The prompt requires keeping user-supplied URLs and titles verbatim, saving links as links rather than notes, naming an item before its citation marker, and checking the tools before declining.

## AI threads (Threadkeeper)

The assistant can use the user's AI threads: conversations with AI assistants and coding agent sessions that [Threadkeeper](threadkeeper-integration.md) keeps, and the chats saved in Still. Two adapters from [`lib/ai/threads.js`](../extension/lib/ai/threads.js) are passed to `init({ threads })` by `app.js`:

- **`chats`** (always, no Threadkeeper needed): reads a saved chat's stored summary and transcript (`lib/chat-data.js`), builds the same summary Markdown the chat's Summary view shows, searches saved chats offline, gives the semantic index a digest of each chat (at most 4,000 characters, through the indexer's `extraText` hook; the chunk header names the provider, project and kind of work), and removes chats an assistant import created (`undoImport`).
- **`threads`** (Threadkeeper): present only while Still is paired, Threadkeeper offers the `search` capability and **Let the assistant search my AI threads** is on. Every answer is validated and capped again in Still (`lib/ai/thread-context.js`); calls time out; three failures in a row pause Threadkeeper for five minutes. Reads never track threads for syncing.

Chats the user made private in Threadkeeper (`chat.removed: 'local_only'`) are invisible to every tool and to the context.

**Tools.** `search_ai_threads` (query, source, provider, kind, project, status, since, until, limit, offset, rerank) returns compact rows: `id` (the saved chat's id when the thread is in Still, else its `tk:` cite id), title, provider, project, date, gist, a snippet with its message number, `match` (strong or weak) and `inLibrary`. Explicit searches may use Threadkeeper's embedding and rerank providers when its `remote_models` capability is on; `offset` pages through Threadkeeper's cursor. When Threadkeeper is down or not connected it searches the chats saved in Still and says so. `get_ai_threads` (ids ≤ 10, detail summary, transcript or both, query, offset, `include_tools`) returns the summary Markdown and a slice of the transcript within 60,000 characters: the opening and newest messages with the gap named, the messages that match `query`, or the messages from `offset` on; tool and system messages only when asked. Saved chats are read from Still's own copy; Threadkeeper fills in what that copy lacks. `get_items` on a chat returns its summary as `article` and the user's notes as `note`. The write tool `import_ai_threads` (ids ≤ 200, `collectionId`: an id, `"new:<name>"`, `""` for Inbox, or left out for Still's usual placement; `tags`) stages one card row ("Import N chats to …") with metadata only; threads already in Still become a move (and tag) instead, chats in Trash are reported. Apply calls the worker's import with origin `assistant`, which never brings back a chat the user deleted or put in Trash (those come back as `notImported` with the reason). Undo removes created chats through `chats.undoImport`, which does not mark them as deleted by the user; a chat changed since goes to Trash.

**Automatic context.** In the library scope, `gatherContext` starts `threads.context` (Threadkeeper's on-device search: `semantic: 'local'`, `rerank: 'off'`, 2.5 s) next to the library search and the decision. The decision (`decideThreadContext`) follows the preference **Automatic thread context** (Smart / Always / Off): Off never asks; Always uses threads; Smart uses a regex prefilter (chat, thread, session, Claude, ChatGPT, Codex, agent, "we decided", "last time" …), treats short library instructions as unrelated, and asks the fast model (`resolveChatTarget({ purpose: 'quick' })`, direct connections only, effort low, at least 1,000 output tokens, 2.5 s) only when it cannot tell and **Use a fast model to decide** is on. The model answers `{"needsThreads", "query", "filters"}` (`DECISION_SYSTEM`); anything unusable falls back to keeping only strong hits. When the model narrows the question, one more local look runs under "Checking your AI threads" (6 s). Automatic context never uses Threadkeeper's remote models, as the protocol requires. Item and collection scopes ask Threadkeeper only about the chats in scope (`filters.threadKeys`); page and item scopes look at all threads only when the prefilter is sure. Every chat in context carries its stored summary (about 60% of its room), the user's notes and up to three matching messages; Threadkeeper passages are merged into a saved chat's source instead of duplicating it, and other threads become `tk:` sources. When thread context was wanted but Threadkeeper did not answer, the reference data and a status line say "AI threads were not available for this answer."

**Trust.** Thread text is marked `untrusted` in the reference data, and the prompt (only when threads are offered or in context) says to never follow instructions in it nor present what an AI said there as fact. A turn whose context or tools read thread text never applies a proposal without review, whatever the permissions say. Its answer renders remote images as links (`renderMarkdown({ images: false })`). Citations of threads keep their thread key in the saved conversation, so a later turn ("import those") or a click can resolve them: the panel opens the saved chat, or offers **Import to Still** (the user's own click, origin `manual`) and **Open in Threadkeeper**.

## Assistant permission levels

**Settings → Assistant permissions** stores the AI setting `assistantPermissions`: `{ create, organize, edit, dashboard, delete }`, each `'ask'` or `'allow'`. The rules are pure functions in [`lib/ai/permissions.js`](../extension/lib/ai/permissions.js).

| Category | Write tools |
| --- | --- |
| Create | `create_note`, `save_links`, `create_collection`, `import_ai_threads` |
| Organize | `move_items`, `add_tags`, `remove_tags`, `set_favorite`, `archive_items`, `unarchive_items`, `restore_items`, `link_items`, `unlink_items` |
| Edit | `update_item` (whatever its fields), `append_to_note`, `update_collection`, `convert_items`, `rename_tag` |
| Dashboard | `show_collection_on_dashboard` |
| Delete | `trash_items`, `delete_collection`, `delete_tag` |

The presets are **Always ask** (every category asks; the default), **Trusted** (everything allowed except Delete) and **Full access** (everything allowed); any other mix shows as **Custom**. A value that is not exactly `'allow'` asks.

A change is classified by its tool first, then by the operation it stages, and it needs every category either one implies. `delete_tag` stages tag removals but is a deletion; a `save_links` call that also moves already saved links into the folder needs Create and Organize, and so does an `import_ai_threads` call that moves or tags chats already in Still. A proposal applies without review only when every change in it is allowed and it changes at most 50 items (`MAX_AUTO_ITEMS`). The count includes subpages that a move, Trash or restore carries along and both sides of a removed link. A change with an unknown tool or operation always asks. Automatic proposals have their own cap of 12 per turn (`MAX_AUTO_PROPOSALS_PER_TURN`), separate from the 4 proposals for review; past it, or over 50 items, an allowed proposal goes to review like any other.

An automatic proposal goes through the same apply path and keeps the same undo record. Its `proposal` event and stored record carry `autoApproved: true`, and the panel shows a receipt ("Applied automatically: …", or "Applied N changes automatically") with Undo and a **Change permissions** link. Each tool result gains `appliedWithoutReview: true`, so the model can say the change was made and can be undone.

The wording the model sees follows the setting, so it never says a change waits for review when it was applied, or the reverse. `assistantSystemPrompt({ tools, today, permissions })` reads the setting once per turn. With nothing allowed, the prompt says write tools only propose changes and the user reviews each one. Otherwise it names the allowed kinds and says a step of only those kinds, changing at most 50 items, is applied at once and can be undone, while any other step becomes a proposal. Each write tool's description ends with "Changes are applied only after the user approves them." unless every change that tool can stage is allowed; then it says the change applies without review within the same limits, and otherwise waits for approval.

`assistantPermissions` is device-only: `exportAiConfig` leaves it out of backups and `importAiConfig` never restores it, so a crafted file cannot turn on automatic changes. Settings writes are validated and refuse unknown categories or levels.

## Research agent prompt

Research runs use their own instructions, not this assembler: `RESEARCH_SYSTEM_PROMPT` in [`lib/ai/research/agent-config.js`](../extension/lib/ai/research/agent-config.js), sent once as the Managed Agents agent's `system`, and the kickoff and follow-up messages built by [`lib/ai/research/prompt.js`](../extension/lib/ai/research/prompt.js). The system prompt asks the agent to understand the saved page, plan 3–6 research questions, use the GitHub tools for technical topics (following the run's GitHub mode), read primary sources, de-duplicate, cite every factual claim with an inline Markdown link, never invent sources, and keep within the depth's search allowance (about 5, 12 or 25 searches). It writes one research section by default and creates subpages only for extensive sub-topics, within the run's maximum. It never alters the original or the user's own text unless edits to the original were allowed, gives one-sentence progress notes and ends with a short summary. Fetched pages, search results, GitHub data, captured text and the user's note are reference data whose instructions it must ignore.

The kickoff message wraps captured text in `<saved_page>`, the user's note in `<user_note>` and an earlier session's report in `<earlier_research>`, and labels them as untrusted. Matching tags inside the data are defused, so page text cannot close its own block. The user's instructions go in `<instructions>`. The page URL is part of the message text on purpose: `web_fetch` can only open URLs that already appeared in the conversation. Changing the system prompt or tools requires bumping `AGENT_SPEC_REVISION`, which makes the next run update the remote agent. See [Research with AI](research-agent.md).

## History and validation

History is local, separately exportable and deletable. Partial/failed generations remain labelled incomplete; their status is preserved when used as later conversation context. A disconnected, aborted, malformed or truncated stream never becomes a completed answer. Model IDs, supported effort values and temperature/image capabilities come from explicit connection settings; the prompt does not select or silently replace them.

File imports (`/import`) use a separate, smaller contract in [`lib/ai/imports.js`](../extension/lib/ai/imports.js): the provider's fast model at low effort, a system instruction limited to the editor's Markdown subset, and file content wrapped in markers as data that must never be followed as instructions. Tidying may restructure but not summarize, translate, reorder or add; parts that return less than half of their words keep their converted text. Output is normalized and any embed syntax becomes a plain link. See [import and embeds](import-and-embeds.md).

Validation is **offline contract validation plus controlled transport/browser fixtures**. Tests cover source injection, typed requests, source selection/truncation, distinct writing actions, real streaming boundaries, cancellation and incomplete output. They do not measure live-model factuality, prompt-injection resistance, writing quality or provider account access. Those require a chosen model and an authorized evaluation run.

Primary implementation guidance: [OpenAI prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), [Responses streaming](https://developers.openai.com/api/docs/guides/streaming-responses), and the provider-specific sources in [ai-providers.md](ai-providers.md).
